# niwa の設計哲学

maku（幕間機）と t8lab（譜面を持たない楽器）で、別々に言葉にしてきた考え方を1つにまとめたもの。
niwa に載る CFW（最初は LOFI）は、ここに当てて機能を採るか決める。破るときは、その CFW の `docs/decisions.md` に理由を1行残す。

出どころ：maku `docs/ABOUT.md` `docs/SPEC.md`、t8lab `docs/SPEC.md`（思想）`docs/decisions.md`（2026-10-11 思想・対象）。

## 1. 楽器の約束（どの CFW も守る）

| 約束 | 中身 | maku | t8lab |
| --- | --- | --- | --- |
| **自走する** | 設定してから鳴らすのではない。電源を入れたらもう鳴っている | 起動ごとにランダムな「世界」 | 起動・HOME で図鑑の位置を引く |
| **外れない** | 何をしても破綻しない。音はスケールの中、骨格は必ず鳴る | `maku_note()` はスケール度数しか返さない | 骨格（確率1）は揺らぎ最大でも鳴る |
| **育つ** | 残すのは「好み（傾向）」だけ。曲・パターン・アンドゥは残さない | REC のいいね16件、振り直しがいいねに寄る | 同じ形のいいね16件 |
| **向きだけを約束する** | 1つのパラメータの細かい値に価値はない。右へ回すほど盛り上がる | 0〜127、単位なし | 同じ |
| **戻らない・書かない** | ステップ入力・保存・アンドゥを作らない | — | ステップ入力なし、パターン保存なし |

`docs/decisions.md` の「自走・外れない・育つ」はこの表の上3行。

## 2. 機能を採るかの判断軸

新しい機能は、次の2つの問いに当てる（t8lab SPEC）。どちらかが「はい」なら、作らないか、形を変える。

1. **人に決めさせていないか。** 選択肢・モード・設定を足すと、演奏者は鳴らす前に決めることになる。
2. **記録を増やしていないか。** 保存するもの・覚えておくものが増えると、「育つ」以外の状態が生まれる。

例：トラックごとの send つまみは作らない。send の量は、ほかの状態（キット・密度・ゴースト）から決まる（t8lab）。

## 3. 対象

- 主な対象：場に音を流す人（DJ イベントの転換・幕間・つなぎ）。
- 対象外：曲を作り込みたい人・再現性が欲しい人。そういう人には Felucca 本体がある。

## 4. 操作の哲学

- **1つのボタンは1つの動詞。** 押せばすぐ音で返る。上段 = 変化の動詞（押している間、または押したあと一定時間）、下段 = 残る操作。
- **画面遷移もメニューもない。** 設定メニューだけは例外で、普段は見えない場所に置く（maku：HOME + OCT−）。
- **つまみの役割は、押している間だけ変わる。** 離せば戻る。状態を覚えるものは例外として扱い、LED と見出しで見せる。
- 詳しい作法は [UI.md](UI.md)。

## 5. 作り方の哲学

- **耳で決める値はコードに埋めず、表（設定ファイル・定数の1か所）に出す。** 実装した人が決めずに、聴き比べの用意をして作者に渡す（t8lab PLAN）。
- **決めたことは decisions.md に1行。** 日付 + 決めたこと + ダッシュの後に理由。仕様書（SPEC など）は「いまのコードがすること」だけを書き、経緯は decisions.md に移す（maku 2026-10-11）。
- **実機で確かめていないことは、確かめていないと書く。** 「コードから読んだ」「ホストで測った」「実機で確認」を区別する（maku の decisions.md の書き方）。
- **一段ずつ main へ。** 各段でテストとエミュレーターが動く状態を保つ。
